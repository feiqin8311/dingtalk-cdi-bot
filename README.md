# README

本文档只讲代码流程，不讲项目背景。

重点说明：

- 程序入口怎么走
- 发货单模式怎么处理
- 不拼箱怎么处理
- 拼箱怎么处理
- 最终结果表是怎么生成的


## 1. 入口流程

界面入口在 [Ui_PyQt.py](/mnt/d/Projects/Automation/Logistics-Department/Dingtalk-Cdi-Bot/Ui_PyQt.py)。

点击“生成报关资料”后，核心流程在 `process_data()`：

1. 收集界面路径
2. 判断是发货单模式还是备货单模式
3. 判断是否拼箱、是否登记、是否生成申报文件
4. 启动 `ProcessingThread`

线程里会分两条主线：

- 发货单：调用 [Invoice_Data.py](/mnt/d/Projects/Automation/Logistics-Department/Dingtalk-Cdi-Bot/Invoice_Data.py)
- 备货单：调用 [Stock_Preparation.py](/mnt/d/Projects/Automation/Logistics-Department/Dingtalk-Cdi-Bot/Stock_Preparation.py)

本文重点只讲发货单，即 [Invoice_Data.py](/mnt/d/Projects/Automation/Logistics-Department/Dingtalk-Cdi-Bot/Invoice_Data.py)。


## 2. 发货单主流程

主入口函数：

- `CustomsDeclaration.generate_all_documents()`

执行顺序：

1. 设置 `self.lcl_flag`
2. 记录日志
3. 根据 `flag` 判断：
   - `True` -> `lcl_situation()`，即拼箱
   - `False` -> `process_invoice()`，即不拼箱
4. 上面两个函数执行完以后，都会生成 `self.result_df`
5. 后续所有 Excel Sheet 都基于 `self.result_df` 生成
6. 如果开启申报文件，则调用：
   - `copy_declaration_template_file()`
   - `fill_declaration_template_file()`
7. 如果开启登记，则调用：
   - `register_all_documents()`


## 3. 发货单模式的公共前置步骤

无论拼箱还是不拼箱，都会先调用：

- `get_basic_information()`

这个函数负责准备两类数据。

### 3.1 公共业务信息，写入 `self.shipping_details`

主要包括：

- `today`
- `mark`
- `country_zh`
- `country`
- `invoice_number`
- `recipient`
- `logistics_provider`
- `Logistics_center`
- `transportation_method`
- `brand`
- 公司主体相关信息

### 3.2 三张基础 DataFrame

返回值是：

- `invoice_df`
- `invoice_details_df`
- `product_df`

其中：

- `invoice_df`
  来源于发货单的 `装箱信息`

- `invoice_details_df`
  来源于发货单的 `发货单详情`

- `product_df`
  来源于 `产品信息单证专用.xlsx`


## 4. `get_basic_information()` 的关键处理

### 4.1 发票号来源

发货单模式里，发票号取自：

- `发货单详情` 的 `物流商单号`

程序默认这票发货单只有一个有效的物流商单号。

### 4.2 品牌和公司主体

程序读取 `店铺`，再映射到公司主体。

当前映射逻辑大致是：

- `EZARC` -> 易达
- `LIBRATON` / `PACMANN` -> 鲁米亚
- `SIXPRAY` -> 六浪
- `TOLESA` -> 匠晟
- 默认 -> 素桐

一旦主体确定，后面这些都会跟着切换：

- 报关单价 Sheet
- 发票抬头
- 发货人
- 银行信息
- 申报模板
- 平台编码

### 4.3 站点和收件人

程序先取国家，再取物流中心编码，再去 `全站点地址.xlsx` 里匹配收件人。

### 4.4 装箱信息里的体积兜底

如果 `总体积（m³）-箱子 == 0`，程序会先改成 `0.01`。

这一步只是防止后续体积计算直接变成 0，不影响拼箱判断。


## 5. 不拼箱流程

不拼箱走：

- `process_invoice()`

这条线比较直接，逻辑可以拆成 7 步。

### 5.1 先获取基础数据

调用：

- `get_basic_information()`

得到：

- `invoice_df`
- `invoice_details_df`
- `product_df`

### 5.2 如果同一个 SKU 出现多次，先按 SKU 汇总

汇总字段包括：

- `发货数量`
- `箱数`
- `总体积（m³）-箱子`
- `总重量（kg）-箱子`

保留第一条的字段包括：

- `单箱数量`
- `箱子毛重（kg）`
- `箱子长度（cm）`
- `箱子宽度（cm）`
- `品名`

### 5.3 计算整票运费

程序取：

- 总体积合计
- 总重量合计

调用 `calculate_shipping_costs()` 计算整票运费。

### 5.4 按口径分摊运费

运费分摊有两种口径：

- 按体积
- 按重量

最终会生成一列：

- `运费分摊`

### 5.5 合并基础资料

程序把 `product_df` 和 `品名.xlsx` 对应信息并进来，得到：

- 报关中文品名
- 英文品名
- HS CODE
- 单位
- 货源地
- 供应商名称
- 材质
- 申报单价

### 5.6 计算报关结果所需字段

主要包括：

- `申报总价`
- `箱子总毛重（kg）`
- `总PCS`
- `是否含金刚石`

### 5.7 最后按报关品名汇总

分组维度是：

- `报关中文品名`
- `是否含金刚石`

最终形成 `result_df`。

这里的关键点是：

- 不拼箱时，箱数基本沿用原始装箱信息累计结果
- 不会再额外做“按重量重新估箱数”


## 6. 拼箱流程

拼箱走：

- `lcl_situation()`

这是和不拼箱最大的区别所在。

拼箱不是简单汇总，而是：

1. 先识别共箱关系
2. 再按重量分摊箱重和体积
3. 再按报关品名重新汇总
4. 最后重新分配箱数


## 7. 拼箱流程详细步骤

### 7.1 先获取基础数据

和不拼箱一样，先调用：

- `get_basic_information()`

### 7.2 对重复 SKU 先重算发货数量

调用：

- `update_shipment_quantity()`

规则是：

- 如果同一个发货单号里某个 SKU 重复出现
- 则 `发货数量 = 箱数 * 单箱数量`

这一步是拼箱模式特有的预处理。

### 7.3 合并产品资料

程序会把这些字段并进来：

- `报关中文品名`
- `单品毛重(g)`
- `外箱规格长(cm)`
- `外箱规格宽(cm)`
- `外箱规格高(cm)`
- `单箱数量(pcs)`
- `材质`

然后转换出：

- `单品毛重(kg)`

### 7.4 先算每行自己的理论总体积

公式是：

`总体积 = 长 * 宽 * 高 / 单箱数量(pcs) * 发货数量 / 1000000`

这是按产品资料反推出的体积，不是直接用原始装箱信息的 `总体积（m³）-箱子`。

### 7.5 合并申报单价，生成基础明细

会继续算：

- `总PCS`
- `申报总价`
- `是否含金刚石`

### 7.6 先做一次“按报关品名”的初步汇总

分组维度：

- `报关中文品名`
- `是否含金刚石`

这里先生成一个中间汇总 `sum_dict`，保存：

- 发货数量
- 总PCS
- 申报总价
- 总体积
- 箱数
- 代表 SKU
- 长宽

注意：

这里的箱数还不是最终结果里的箱数。


## 8. 拼箱是怎么识别的

程序不是靠人工标记“这两个 SKU 是拼箱”，而是通过箱信息自动识别。

分组字段是：

- `发货单号`
- `箱数`
- `箱子毛重（kg）`
- `箱子长度（cm）`
- `箱子宽度（cm）`
- `箱子高度（cm）`
- `总重量（kg）-箱子`
- `总体积（m³）-箱子`

如果一组里有多行，即：

- `len(group) > 1`

程序就认为这些 SKU 共用同一批物理箱，也就是拼箱。

如果一组里只有一行，即：

- `len(group) == 1`

则程序认为这行不是拼箱。


## 9. 拼箱时怎么分摊箱重和体积

对真正的拼箱组，程序会按每个 SKU 的货重占比分摊。

先算：

- `单品毛重汇总 = 单品毛重(kg) * 发货数量`

然后算：

- `实际箱子毛重（kg）`
- `实际CBM（m³）-箱子`

逻辑是：

- 同一批物理箱里的总毛重、总体积不能让每个 SKU 都重复拿一份
- 要按货重占比拆开

分摊完成后，会把分摊结果回写到 `merge_df`。


## 10. 拼箱后为什么还要重算总重量和总体积

因为原始的：

- `总重量（kg）-箱子`
- `总体积（m³）-箱子`

对应的是整批共箱数据。

分摊后，每个 SKU 自己的箱重和体积已经变了，所以程序会重算：

- `总重量（kg）-箱子 = 箱子毛重（kg） * 箱数`
- `总体积（m³）-箱子 = CBM（m³）-箱子 * 箱数`

这里得到的是“分摊后口径”的重量和体积。


## 11. 拼箱后怎么生成最终报关汇总

程序会再次按：

- `报关中文品名`
- `是否含金刚石`

汇总，主要汇总：

- `总重量（kg）-箱子`
- `总体积（m³）-箱子`

然后把这些结果写回前面的 `sum_dict`。


## 12. 拼箱时箱数是怎么重算的

这是拼箱里最关键的一步。

对于被识别为拼箱的报关品名组，程序会重新计算箱数，规则是：

- `箱数 = floor(总重量 / 15)`
- 如果结果为 0，则先给 1

所以拼箱里的最终箱数，不是简单沿用原始装箱信息。

它是：

- 先按共箱关系分摊重量
- 再按报关品名的总重量反推出箱数

这和不拼箱完全不一样。


## 13. 拼箱为什么还会有“箱数回补”

原因很简单：

- 原始物理箱总数
- 按 `总重量 / 15` 重新算出来的报关箱数总和

这两个数通常不完全一样。

所以程序会做一次“回补”：

1. 先记原始拼箱总箱数 `lcl_total_boxes`
2. 再减去各报关品名重算后的箱数
3. 把差值补回某个拼箱品名

因此拼箱模式里，某个品名最后的箱数，可能是：

- 原始汇总箱数
- 按重量重算后的箱数
- 再经过回补修正后的箱数

这就是为什么拼箱的箱数比较难直观看懂。


## 14. 拼箱结果里的箱数应该怎么理解

拼箱结果里的 `箱数`，不要直接理解成“这个品名有没有装箱”。

更准确地说，它表示：

- 这个报关品名在最终报关结果里，被分配到多少箱数份额

也就是说：

- 原始物理箱是共用的
- 最终报关展示时，程序又做了一次按品名分配

所以拼箱时：

- 某个品名有重量
- 某个品名有体积
- 但它的箱数仍然可能是 0

从代码逻辑上这是允许出现的。


## 15. 拼箱和不拼箱的本质区别

### 不拼箱

- 先按 SKU 汇总
- 再按报关品名汇总
- 箱数基本沿用原始数据累计结果
- 不额外做按重量重算箱数

### 拼箱

- 先识别哪些 SKU 共箱
- 按单品毛重占比分摊箱重和体积
- 再按报关品名汇总
- 再按总重量重新估箱数
- 最后再做箱数回补

所以拼箱的结果更像“估算分配结果”，不拼箱的结果更像“原始装箱结果的整理版”。

虽然最终结果里箱子总毛重不同，但长宽一样，且这两行都来自拼箱重分配之后的结果。

结合你的说明，“下面两个是拼箱的”，这里可以按这个案例理解为：

- 它们原来在同一批共箱数据里
- 只是后面按货重分摊后，各自拿到的总毛重不同了


## 25. 这个案例里程序是怎么给后两行分摊重量的

对拼箱组，程序先算：

- `单品毛重汇总 = 单品毛重(kg) * 发货数量`

然后按占比去分：

- `实际箱子毛重（kg）`
- `实际CBM（m³）-箱子`

也就是说：

- `80921501` 最后拿到了 `12.16 kg`
- `81619601` 最后拿到了 `1.84 kg`

两者加起来正好是：

- `12.16 + 1.84 = 14.00 kg`

这说明从这次结果看，后两行非常像是来自同一批总毛重约 `14kg` 的拼箱数据，再被程序按占比分开了。


## 26. 这个案例里为什么 `81619601` 是 1 箱

程序对拼箱汇总后的每个报关品名，会重新估算箱数：

- `箱数 = floor(总重量 / 15)`
- 如果结果是 `0`，先给 `1`

看 `81619601`：

- 总毛重是 `1.84 kg`
- `1.84 / 15 = 0.x`
- 向下取整后是 `0`
- 所以程序先给它 `1 箱`

这和你现在最终结果里的：

- `箱数 = 1`

是一致的。


## 27. 这个案例里为什么 `80921501` 最后会变成 0 箱

先看这行的总毛重：

- `12.16 kg`

按同样规则：

- `12.16 / 15 = 0.x`
- 向下取整后是 `0`
- 理论上程序先给它 `1 箱`

也就是说，单看“按重量重算箱数”这一步，`80921501` 不应该直接变成 `0`。

它之所以最后变成 `0`，是因为后面还有一步：

- `箱数回补`

程序会先计算：

- 原始拼箱总箱数
- 重算后的拼箱总箱数

然后求差值，再把这个差值补回某一个拼箱组。

所以这个案例里，最可能发生的是：

1. `80921501` 先被算成 `1 箱`
2. `81619601` 也先被算成 `1 箱`
3. 但原始共箱总箱数不允许这两个都各占 1 箱
4. 程序在回补时把其中一个扣掉
5. 最终 `80921501 = 0`

所以这行结果的真正含义不是：

- “切割片没有装箱”

而是：

- “切割片在最后的报关箱数分配中，没有被单独分到箱数份额”


## 28. 这个案例里为什么 `80921501` 会出现 `inf`

因为后面很多字段都拿 `箱数` 当分母。

比如：

- `每件毛重KGS = 箱子总毛重 / 箱数`
- `箱子高度（cm） = 体积 / 长 / 宽 / 箱数`

代入 `80921501` 这行：

- 箱子总毛重：`12.16`
- 箱数：`0`

那就会变成：

- `12.16 / 0 = inf`

高度也是一样：

- `0.02 / 29 / 25 / 0`
- 分母有 0
- 所以也是 `inf`

于是你最终看到：

- `每件毛重KGS = inf`
- `每件净重KGS = inf`
- `共重净重KGS = NaN`
- `箱子高度（cm） = inf`


## 29. 这个案例里第一行为什么没有问题

看第一行：

- `80290012`
- `箱数 = 12`
- `箱子总毛重 = 198.86`

这说明：

- 这组要么不是拼箱
- 要么即使参与汇总，也没有在回补时被扣成 0

后面所有按 `箱数` 做分母的计算都正常，所以：

- 每件毛重
- 每件净重
- 高度
- 体积

都能正常算出来。


## 30. 这个案例里可以得出的结论

基于你这次的控制台输出，这个案例至少能说明下面几点：

### 结论 1

`26EA056` 这票在拼箱模式下，最终形成了 3 个报关汇总组。

### 结论 2

其中后两组大概率来自同一批共箱数据，因为：

- 你明确说明它们是拼箱
- 它们的结果表现也符合“同批共箱后被二次分配”的特征

### 结论 3

`80921501` 的 `0 箱` 不是原始装箱数据直接给出来的，而是：

- 拼箱分摊
- 按重量重算箱数
- 箱数回补

这三步之后的最终结果。

### 结论 4

`inf` 和 `NaN` 不是独立问题，它们只是 `箱数 = 0` 的连带结果。


## 31. 以后如果还要手工复盘类似案例，建议按这个顺序看

针对任何一票拼箱发货单，都按下面顺序排：

### 第一步：先看原始装箱信息

确认哪些行的这些字段完全相同：

- 箱数
- 箱子毛重
- 长宽高
- 总重量
- 总体积

这些相同的行就是程序眼里的“拼箱组”。

### 第二步：看每个 SKU 的单品毛重和发货数量

因为程序分摊箱重和体积，用的是：

- 单品毛重 × 发货数量

### 第三步：看这些 SKU 最后归到了哪些报关中文品名

因为最终结果不是按 SKU，而是按：

- 报关中文品名
- 是否含金刚石

### 第四步：看重算后的箱数

对拼箱组，程序会按：

- 总重量 / 15

重算箱数。

### 第五步：看有没有发生箱数回补

如果最后某个品名箱数和你直觉不一致，通常就要去看回补这一步。
