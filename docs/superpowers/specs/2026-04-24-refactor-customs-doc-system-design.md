# 报关单证系统重构设计

**日期**: 2026-04-24

**目标**
- 减少 [Invoice_Data.py](/mnt/d/Projects/dingtalk-bot/dingtalk-cdi-bot/Invoice_Data.py) 与 [Stock_Preparation.py](/mnt/d/Projects/dingtalk-bot/dingtalk-cdi-bot/Stock_Preparation.py) 的重复逻辑
- 降低新增业务规则、单据类型、登记字段时的改动成本
- 在不破坏现有 UI 和业务结果的前提下，渐进式重构系统结构

## 当前问题

当前代码结构的主要问题不是“功能不工作”，而是“功能堆叠在错误的边界上”。

- 两个核心脚本都以单个超大类 `CustomsDeclaration` 承载所有职责
- 业务计算、Excel 读写、模板填充、分页设置、登记写入、日志统计混杂在同一个文件里
- 发货单与备货单流程存在大量重复代码，但又夹杂少量差异规则
- 修复同类问题时需要双份修改，极易出现一边修复、一边遗漏
- UI 层目前直接依赖大类主流程，导致底层结构调整成本偏高

这类结构会带来三个直接后果：

- 小改动需要跨多个大函数查找影响点
- 新需求更容易通过复制旧逻辑实现，进一步放大重复
- 缺陷定位依赖开发者记忆，而不是依赖清晰模块边界

## 重构原则

本次重构采用“渐进式重构”，不是重写。

约束如下：

- 不先推翻现有 UI 入口
- 不先统一所有业务规则
- 不追求第一阶段就把所有代码拆完
- 先抽公共能力，再梳理业务边界，再瘦身主流程
- 每一阶段都要求可运行、可验证、可回退

本次设计优先满足两个目标：

- 减少重复逻辑
- 降低新增规则的改动范围

不作为第一优先级的事项：

- 完整领域建模
- 全量类型系统改造
- UI 架构升级
- 一次性彻底删除旧接口

## 推荐架构

推荐结构为“共用基础组件，保留独立主流程”。

原因：

- 发货单和备货单共享大量基础能力，但并非完全相同
- 如果强行合成单一超级流程，短期去重，长期会把差异规则塞进大量条件分支
- 保留两个 flow，可以让差异停留在流程编排层，而不是污染公共组件

目标目录结构如下：

```text
app/
  core/
    models.py
    logging.py
    metrics.py
    excel_io.py
    page_setup.py
    template_files.py
  services/
    basic_info_service.py
    declared_price_service.py
    freight_service.py
    elements_service.py
    register_service.py
  renderers/
    detailed_list.py
    packing_list.py
    bill.py
    contract.py
    customs_declaration.py
    elements_sheet.py
  flows/
    invoice_flow.py
    stock_flow.py
```

## 模块职责

### 1. `app/core`

放置纯通用基础设施，不承载具体业务规则。

- `models.py`
  - 定义共享数据结构
  - 例如 `ShippingContext`、`DocumentResult`、`RegisterTarget`
- `logging.py`
  - 封装日志输出路径、日志写入、统一格式
- `metrics.py`
  - 封装调用统计追加逻辑
- `excel_io.py`
  - 负责 Excel 缓存读取、工作簿打开、公共列清洗辅助
- `page_setup.py`
  - 负责分页预览与打印缩放的持久化设置
  - 负责可选的 WPS/Excel COM 兼容处理
- `template_files.py`
  - 负责模板复制、模板路径选择、模板写入公共辅助

约束：

- `core` 不依赖 `flows`
- `core` 允许被所有层调用
- `core` 中函数应尽量无业务状态或仅依赖显式传参

### 2. `app/services`

承载业务计算，不直接控制 UI，不直接编排完整文档生成流程。

- `basic_info_service.py`
  - 从输入单据和产品表提取基础上下文
  - 输出统一上下文对象
- `declared_price_service.py`
  - 处理申报单价表读取与不同公司的取价规则
- `freight_service.py`
  - 处理运费口径、分摊规则、币种影响
- `elements_service.py`
  - 处理要素表匹配
- `register_service.py`
  - 处理登记表写入、重复校验、行数校验、公共格式写入

约束：

- `services` 只处理一类业务
- 输入输出尽量显式
- 不负责最终文档文件命名
- 不负责 UI 提示

### 3. `app/renderers`

只负责把已有数据渲染到 sheet，不重新做业务推导。

- 一个 renderer 对应一个 sheet 类型
- renderer 输入为工作簿对象 + 标准化数据 + 渲染参数
- renderer 不主动读取源 Excel
- renderer 不承担登记逻辑

这层的目标是把现在大文件里的 `add_*_sheet` 系列方法解耦出来。

### 4. `app/flows`

只负责流程编排。

- `invoice_flow.py`
  - 面向发货单
- `stock_flow.py`
  - 面向备货单

flow 的职责：

- 决定读取哪些 sheet
- 决定拼箱/非拼箱分支
- 调用 service 产出中间数据
- 调用 renderer 生成输出文件
- 调用 register service 完成登记

flow 不负责底层 Excel 工具细节，不负责分页底层实现，不负责日志落盘细节。

## 发货单与备货单的边界

保留两套独立 flow，但共享基础层。

共享内容：

- 日志与统计
- Excel 读取缓存
- 分页设置
- 模板复制/模板填充的公共部分
- 图片插入
- 通用 sheet 渲染辅助
- 登记公共写入逻辑
- 要素匹配
- 运费规则公共部分

保留差异内容：

- 输入 sheet 名称与字段差异
- 基础信息提取逻辑差异
- 发票号来源差异
- 拼箱分摊逻辑差异
- 出运明细/报关开票登记字段映射差异

判断标准：

- 如果某段逻辑只是输入列名不同，应抽到公共组件
- 如果某段逻辑表达的是不同业务规则，应保留在各自 flow 或差异 service 中

## 迁移策略

采用四阶段迁移。

### 阶段 1: 抽公共基础设施

目标：不改变业务结果，先减少重复。

范围：

- 日志与调用统计
- Excel 读取缓存
- 分页设置
- 图片插入
- 模板文件复制与公共填充辅助

产出：

- 两个大文件先引用公共模块
- 首批重复工具方法删除或变为薄包装

### 阶段 2: 抽通用服务

目标：把“计算”从“大类”中拆出来。

范围：

- 申报价处理
- 运费计算
- 要素匹配
- 登记表公共写入

产出：

- 业务计算从类方法转为 service 调用
- 类状态依赖减少

### 阶段 3: 抽 sheet renderer

目标：把 `add_*_sheet` 从主类中移走。

范围：

- 明细单
- 装箱单
- 发票
- 合同
- 报关单
- 要素

产出：

- `generate_all_documents()` 只剩编排
- 渲染逻辑可以独立测试

### 阶段 4: 重组 flow 与 UI 接口

目标：让 UI 不再直接耦合大类实现细节。

范围：

- 发货单 flow
- 备货单 flow
- UI 调用入口适配

产出：

- UI 调用统一入口
- 原 `CustomsDeclaration` 可作为兼容层逐步退役

## 兼容策略

为了降低迁移风险，重构过程中保留兼容外观。

策略如下：

- 旧的 `CustomsDeclaration` 入口在一段时间内保留
- 旧方法内部改为调用新模块
- UI 层在最后阶段再切换到新 flow
- 每抽出一个模块，都要求旧调用方式仍可工作

这样可以避免“一次性替换导致整套流程失稳”。

## 测试策略

测试重点不是追求高覆盖率，而是保护高风险边界。

优先测试：

- 分页设置持久化
- 要素匹配顺序与命中规则
- 申报价选择规则
- 运费计算与分摊
- 登记写入行数校验
- 发货单/备货单主流程的最小 smoke test

建议测试层次：

- 单元测试：`core`、`services`、`renderers`
- 集成测试：`flows`
- 手工回归：UI 主流程、真实模板输出

## 验收标准

阶段性验收不以“文件数量变多”为标准，而以以下指标判断：

- 发货单与备货单重复工具逻辑不再双份维护
- 修改分页、模板、日志、登记等公共能力时只需改一处
- 新增规则时，能定位到明确模块，不必在两个 3000 行文件里同时搜索
- `generate_all_documents()` 和 `register_all_documents()` 的主流程长度明显下降
- 现有关键回归测试保持通过

## 不做的事

本次重构明确不做以下内容：

- 不同时重做 PyQt UI 结构
- 不改业务模板格式
- 不统一所有历史命名问题
- 不一次性把全部旧方法删掉
- 不引入过重框架或容器系统

## 风险与控制

主要风险：

- 迁移过程中把“看似公共、实则有差异”的逻辑抽错
- 类状态过多，拆服务时出现隐式依赖遗漏
- UI 仍然依赖旧方法签名，替换节奏过快会导致运行中断

控制方式：

- 每阶段只抽一类责任
- 先补测试再迁移
- 旧入口保留兼容层
- 优先重构重复率高、业务争议小的模块

## 结论

这次重构不应以“把两个文件拆碎”为目标，而应以“建立稳定边界”为目标。

最合适的路径是：

1. 共用基础组件
2. 保留发货单/备货单独立 flow
3. 渐进式迁移
4. 在每阶段维持现有功能可运行

这样可以在控制风险的前提下，稳定降低重复逻辑，并显著降低后续新增需求的实现成本。
